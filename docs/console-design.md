# 统一管理端设计

## 结论

- 网页管理端，管理芽豆全部产品（yadoA、yadoI……），地址 `https://console.yado1225.top`。
- **纯静态单页应用**：由服务器上已有的 nginx 直接提供文件，不新增后端服务和容器，不占服务器内存。
- 管理端自己不存数据。每个功能直接调用对应后端的管理接口，例如意见反馈调 yado_hub `/v1/admin/feedback/*`。
- 用芽豆统一登录（Logto）登录。管理员资格由各后端判断，目前是 yado_hub 的 `ADMIN_USER_IDS`。

## 为什么不用现成的管理平台

| 方案 | 不用的原因 |
| --- | --- |
| Appsmith、Budibase、ToolJet 等低代码平台 | 自己部署至少要 2 GB 内存，服务器只有 1.6 GB；Retool 是收费的托管服务 |
| Directus、NocoDB 等直连数据库的工具 | 绕过后端的业务规则（如只能重开最新一单），还要另外维护一套登录 |
| Ant Design 等组件库 | 太重，首屏要几百 KB；管理端只有几个页面，用不上 |

## 技术选型：轻量优先

- **Svelte 5 + Vite + TypeScript**：Svelte 在构建时把组件编译成普通 JS，运行时很小。
- **不用组件库，不用路由库**：样式手写，路由是基于 History API 的几十行代码。
- **系统字体**，不加载网络字体；时间格式化用浏览器内置的 `Intl`。
- **唯一的运行时依赖是 `@logto/browser`**，也就是 Logto 官方 SDK。
- **体积预算**：`pnpm build` 后自动检查，JS ≤ 60 KB、CSS ≤ 8 KB（gzip 后），超出就构建失败。
  第一版实测 JS 36 KB、CSS 2.3 KB，其中大部分是 Logto SDK。
- **缓存**：
  - 带哈希的资源缓存一年，`index.html` 每次都向服务器确认；
  - 构建时预压缩 `.gz`，nginx 直接发送。

## 第一版：意见反馈

| 页面 | 内容 |
| --- | --- |
| 登录 | 用芽豆账号登录；不是管理员的账号提示没有权限 |
| 反馈单列表 | 按状态（待处理 / 已处理 / 全部）和产品筛选，按最新消息倒序；侧栏显示待处理数 |
| 对话详情 | 用户全部历史消息，按反馈单分段，附设备信息；可以回复、回复并标记已处理、标记已处理 / 重新打开 |

- 对话页打开时，每 15 秒拉一次新消息（页面可见时才拉），回到页面时立即拉一次。
- 回复的消息 ID 由前端生成，重试时沿用同一个，网络抖动也不会重复回复。
- 手机浏览器可用：侧栏变成顶栏。

## 以后

- **显示用户名**：yado_hub 接入 Logto Management API，列表和详情显示用户名而不只是用户 ID。
- **新功能**：例如 AI 点数管理。在对应后端加管理接口，管理端再加一个导航项和 `modules/<功能>/`。
  - 新后端需要在 `auth.ts` 的 resources 里加上它的 API 资源，在 nginx 的 CSP `connect-src` 里加上它的地址。
- **管理员名单改用 Logto 角色（RBAC）**：等第二个后端有管理接口时再改，届时不再在每个后端各维护一份 `ADMIN_USER_IDS`。
