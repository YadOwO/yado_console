# 统一管理端设计

## 结论

- 网页管理端，管理芽豆全部产品（yadoA、yadoI……），地址 `https://console.yado1225.top`。
- **纯静态单页应用**：由服务器上已有的 nginx 直接提供文件，不新增后端服务和容器，不占服务器内存。
- 管理端自己不存数据。每个功能直接调用对应后端的管理接口，例如意见反馈调 yado_hub `/v1/admin/feedback/*`。
- 用芽豆统一登录（Logto）登录。管理员资格由各后端判断，目前是 yado_hub 的 `ADMIN_USER_IDS`。

## 为什么不用现成的管理平台

| 方案 | 不用的原因 |
| --- | --- |
| Appsmith、Budibase、ToolJet 等低代码平台 | 自己部署至少要 2 GB 内存，服务器只有 1.6 GB；Retool 是收费的托管服务 |
| Directus、NocoDB 等直连数据库的工具 | 绕过后端的业务规则（如只能重开最新一单），还要另外维护一套登录 |
| Ant Design 等组件库 | 太重，首屏要几百 KB；管理端只有几个页面，用不上 |

## 技术选型：轻量优先

- **Svelte 5 + Vite + TypeScript**：Svelte 在构建时把组件编译成普通 JS，运行时很小。
- **不用组件库，不用路由库**：样式手写，路由是基于 History API 的几十行代码。
- **系统字体**，不加载网络字体；时间格式化用浏览器内置的 `Intl`。
- **唯一的运行时依赖是 `@logto/browser`**，也就是 Logto 官方 SDK。
- **体积预算**：`pnpm build` 后自动检查，JS ≤ 80 KB、CSS ≤ 8 KB（gzip 后），超出就构建失败。
  第一版实测 JS 36 KB、CSS 2.3 KB，其中大部分是 Logto SDK；加上 Agent 后 JS 47 KB、CSS 3.7 KB。
  2026-11-09 加完「采纳并开工」时 JS 到了 60 KB 的上限，经维护者同意放宽到 80 KB（原因见 `scripts/check-size.mjs`）。
- **缓存**：
  - 带哈希的资源缓存一年，`index.html` 每次都向服务器确认；
  - 构建时预压缩 `.gz`，nginx 直接发送。

## 第一版：意见反馈

| 页面 | 内容 |
| --- | --- |
| 登录 | 用芽豆账号登录；不是管理员的账号提示没有权限 |
| 反馈单列表 | 按状态（待处理 / 已处理 / 全部）和产品筛选，按最新消息倒序；侧栏显示待处理数 |
| 对话详情 | 用户全部历史消息，按反馈单分段，附设备信息；可以回复、回复并标记已处理、标记已处理 / 重新打开 |

- 对话页打开时，每 15 秒拉一次新消息（页面可见时才拉），回到页面时立即拉一次。
- 回复的消息 ID 由前端生成，重试时沿用同一个，网络抖动也不会重复回复。
- 手机浏览器可用：侧栏变成顶栏。

## 第二个功能：Agent

Mac 上的 agentd（[yado_agents](../../yado_agents)）跑四种自动流程：代码 review、代码清理、产品探索、一次实现。agentd 长轮询 hub 领指令，
有新动态或每小时把状态摘要同步到 yado_hub。管理端调 yado_hub `/v1/admin/agents/*` 看结果；改东西都是「发指令」，Mac 取走执行，页面轮询结果。

页面分两层：**全局的**（总览、待办、想法、运行记录、经验）放在顶部标签里，待办和想法是每天要处理的，标签上带没处理的条数；
**每种流程自己的**（实例、这个流程的运行）在流程页里，从总览的流程卡进。

| 页面 | 内容 |
| --- | --- |
| 总览 `/agents` | 机器在线状态、数据更新时间、立即同步；「运行中 · 排队 · 等你点头」点开看具体运行，没结束的每条写这次做什么、现在在干什么（排队的写在等什么）；待办提醒；每种流程一张卡：模式（推送 / 推新分支 / 只出想法）、实例数与暂停数、下次运行、上次运行的结论，产品探索卡显示没处理的想法数；全局设置（同时跑几次运行、默认模型、思考强度、保留天数，名字说不清的字段下面带一句说明） |
| 流程页 `/agents/flows/<类型>` | 流程说明、暂停 / 恢复整个流程；review 与代码清理：仓库实例列表（立即运行、暂停 / 恢复、设置、删除）与「新建」（流程已定，只选仓库与分支）；产品探索：实例与去「想法」的入口；一次实现：实例与提需求的说明；最后是这个流程的最近运行 |
| 待办 `/agents/inbox` | 按仓库（实例）分组，组标题写仓库名和流程；主审交给你决定的问题（不修 / 交给主审 / 已处理），需要你看一下的运行（知道了；停下来的一次实现还能交给主审）；侧栏显示待办数 |
| 想法 `/agents/ideas` | 产品探索的想法（按产品分组，采纳并开工 / 丢弃 / 已实现，都可以写备注）、产品偏好（作废 / 恢复） |
| 运行记录 `/agents/runs` | 按流程、实例、状态筛选；跨流程看时每条带流程标签，实例显示仓库名 |
| 运行详情 `/agents/runs/<机器>/<运行>` | 结论、提交范围、tokens、问题与主审的理由、每一步、时间线；没结束时可以取消 |
| 经验 `/agents/lessons` | 主审总结的一句话规则：先「通用」再按仓库分组，组标题显示生效中的条数与上限；每条显示命中次数、来源运行、加入日期，可以作废；已作废的收起来，可以恢复 |

- review 与代码清理复审通过的修复、重构直接推到开发分支；「允许推到会触发部署的分支」、检查命令只能在 Mac 上改。挂系列文件夹的实例（一次实现、产品探索）只能在 Mac 上建和删。
- hub 只有摘要：问题详情、修复说明和 diff 只在 Mac 上，详情页提示用 `agentctl report <运行>` 看。
- 经验页面上只能作废、恢复，不能改文字或新增：经验会写进给模型的提示词，这些只能在 Mac 上用 agentctl 做（同检查命令）。
- 「交给主审」可以先补充一段信息（选填，最多 1000 字），Mac 上另开一次运行让主审在修和不修里选一个；运行详情里两边互相链接。
- 停下来的一次实现（Mac 判断已经开始实现、代码还在，`canDelegate`）也能「交给主审」：同一次运行在 Mac 上重新排队，主审看停下的原因定处理办法、实现者照着改，都通过就推 feat 分支、作为新功能回到待办。
- 页面数据是 Mac 最近一次上传时的状态，最多晚一小时；要看最新的点「立即同步」。
- 总览数据各页面共用一份（`overview-store.svelte.ts`）：换页面先显示上次取到的，再在后台刷新；总览、待办、流程页打开期间每 10 秒刷新一次，
  切回页面时立即刷一次。侧栏的待办数跟着总览对齐，另外每分钟自己查一次兜底。
- 待办和想法可以连着处理：点了就先从列表里拿掉，指令立刻发给 hub、在后台等结果，不用等 Mac 回话再点下一条。
  结果按发出的先后一条条查，同一时刻只有一个轮询；没成功的那条会回到列表里并写明原因，写过的备注还在。
- 其他操作（设置、实例、经验）执行期间禁用各操作按钮，避免连点发出重复指令；结果显示在页面底部的提示条上。
- 运行详情的「返回」退回上一页（待办、流程页、运行记录都行），滚动位置和筛选都在；直接打开详情页时才是「运行记录」。
  运行记录页记着上次的列表（含翻过的页），返回时先原样显示，再刷新最新一页。

### 共用的部分

写新页面先用现成的，不要再抄一份。各页面的 `<style>` 只写自己独有的样式。

| 东西 | 在哪 | 用处 |
| --- | --- | --- |
| 通用版式 | `src/app.css` 后半段 | 页面外壳（`.page`）、卡片（`.card`）、列表（`.list`）、左侧色条（`.bar` + `.tone-*`）、条数（`.pill`）、角标（`.badge`）、按钮排（`.btn-row`）、表单行（`.form-row`）等 |
| 页面外壳 | `agents/AgentPage.svelte` | Agent 五个标签页的标题、说明、右上角控件和标签栏 |
| 规则列表 | `agents/RuleList.svelte` | 经验和产品偏好：按组列出，作废 / 恢复 |
| 备注面板 | `agents/NotePanel.svelte` | 待办和想法处理前写备注：说明、备注框、取消与确定 |
| 运行列表 | `agents/RunItems.svelte` | 总览、流程页、运行记录里的运行列表 |
| 总览数据 | `agents/overview-store.svelte.ts` | 各页面共用的一份总览，带实例名、流程名的对照表 |
| 定时刷新 | `lib/poll.ts` | 页面可见时定时做一件事，切回页面时补一次 |
| 刷新角标 | `lib/admin-status.svelte.ts` 的 `refreshBadges` | 数据变了之后顺手刷新侧栏的数字 |

全局的类名会漏进所有页面：页面里自己起的类名不要和 `app.css` 里的重名，除非就是要在它上面加几条。

## 以后

- **显示用户名**：yado_hub 接入 Logto Management API，列表和详情显示用户名而不只是用户 ID。
- **新功能**：例如 AI 点数管理。在对应后端加管理接口，管理端再加一个导航项和 `modules/<功能>/`。
  - 新后端需要在 `auth.ts` 的 resources 里加上它的 API 资源，在 nginx 的 CSP `connect-src` 里加上它的地址。
- **管理员名单改用 Logto 角色（RBAC）**：等第二个后端有管理接口时再改，届时不再在每个后端各维护一份 `ADMIN_USER_IDS`。
